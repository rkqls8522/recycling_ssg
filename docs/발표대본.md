**말할 내용**

함께 중요한 상황이었습니다.

## 슬라이드 3 — 첫 시도와 벽 (1.5분)

**그림**: `02_86_to_17_classes.png` (왼쪽 히스토그램)

**말할 내용**

처음에는 86클래스를 그대로 학습시켰습니다. 결과는 **mAP50-95 0.3765**. 낮았습니다.

클래스별로 뜯어보니 원인이 보였습니다. **86개 중 30개, 그러니까 35% 가

**29개 trial** 을 돌렸고, 0.3765 에서 **0.5209** 로 올랐습니다. 38% 개선이니
의미 있는 수치였습니다.

하지만 0.52 는 서비스에 쓸 수 있는 수준이 아니었습니다. 튜닝으로는
한계가 있다는 게 분명해졌습니다.

## 슬라이드 4 — 전환점: 문제를 다시 정의하다 (2분)

**그림**: `02_86_to_17_classes.png` (오른쪽 막대)

**말할 내용**

여기서 질문을 바꿨습니다.

> "우리 서비스가 정말 86개를 구분해야 하나?"

사용자가 알고 싶은 건 **"이걸 어디에 버리지?"** 입니다. 그런데 86클래스에는
'고철류/골프채', '고철류/기타' 처럼 **배출 방법이 똑같은데 이름만 다른** 항목이
잔뜩 있었습니다. 모델에게 불필요하게 어려운 문제를 풀게 하고 있었던 겁니다.

그래서 배출 방법이 같은 소분류를 묶어 **17개 클래스로 재편**했습니다.
고철류/고철, 종이류/신문지, 페트병/페트병 같은 식으로요.

결과:

| | 86클래스 | 17클래스 |
| --- | --- | --- |
| 클래스당 평균 학습 이미지 | 89장 | **448장** |
| mAP 0.3 미만 클래스 | 30개 (35%) | **0개** |
| mAP50-95 | 0.5209 | **0.8349** |

**Optuna trial 29회보다, 클래스 정의를 바꾼 것 하나가 훨씬 효과가 컸습니다.**

이게 이 프로젝트에서 얻은 가장 큰 교훈입니다. 모델을 손대기 전에
**문제를 제대로 정의했는지** 먼저 봐야 한다는 것.

> **주의해서 말할 것**: 86클래스와 17클래스는 클래스 정의가 다르므로 mAP 를
> 엄밀하게 1:1 비교할 수는 없습니다. 다만 "서비스가 필요로 하는 작업"을
> 기준으로 보면 후자가 훨씬 잘 푼 것이 맞습니다.

## 슬라이드 5 — 이미지 증강 실험 (2분)

**그림**: `04_augmentation_effect.png`

**말할 내용**

다음은 데이터를 늘리는 쪽이었습니다. 증강 기법을 **37가지 설정으로 47번**
돌려 비교했습니다. YOLO 내장 증강과 OpenCV 로 직접 만든 정적 증강을 모두 포함해서요.

결과는 기법마다 뚜렷하게 갈렸습니다.

| 증강 | 효과 (증강 OFF 대비) |
| --- | --- |
| **mosaic** | **+0.0415** |
| mosaic+mixup+cutmix | +0.0367 |
| YOLO 기본 증강 | +0.0275 |
| scale | +0.0111 |
| **motion blur** | **−0.0006** |

여러 이미지를 한 장면으로 합치는 **mosaic 계열이 가장 효과적**이었습니다.
반대로 화질을 떨어뜨리는 motion blur 는 오히려 성능을 깎았습니다.

생각해 보면 당연합니다. 실제 사용자는 흐릿한 사진을 올리기보다 물건을
제대로 찍어 올리고, 한 장면에 여러 물건이 있는 경우가 많으니까요.

## 슬라이드 6 — 트러블슈팅 ①: 숫자가 이상하다 (2분)

**그림**: `05_close_mosaic_bug.png`

**말할 내용**

그런데 증강 실험 결과를 검토하다 이상한 걸 발견했습니다.

**서로 다른 4개 증강 설정이 소수점 6자리까지 완전히 똑같은 점수**를 냈습니다.

```
Y08 yolo_mosaic               0.807046
Y09 yolo_mixup                0.807046
Y10 yolo_cutmix               0.807046
Y14 yolo_mosaic_mixup_cutmix  0.807046
```

우연일 수 없는 값이었습니다. 원인을 찾아보니 `close_mosaic` 이라는 설정의
의미를 잘못 알고 있었습니다.

> `close_mosaic=N` = **마지막 N epoch 동안** mosaic 을 끈다

Ultralytics 기본값이 **10** 인데, 저희가 `epochs` 를 **10** 으로 뒀습니다.
그러니까 **처음부터 끝까지 mosaic 이 꺼진 채** 학습된 겁니다.
mosaic 계열 설정들이 전부 "증강 없음"과 같아져서 동일한 점수가 나온 것이고요.

**즉, 그때까지의 mosaic 실험 결과는 전부 무효였습니다.**

`CLOSE_MOSAIC_EPOCHS = round(EPOCHS * 0.2)` 로 고쳐서 전체의 20% 구간에서만
끄도록 했고, 다시 실험하니 **그제서야 mosaic 이 1위**로 올라왔습니다.

이 경험에서 배운 건, **의심스러운 숫자는 끝까지 파야 한다**는 것입니다.
그냥 "우연히 비슷하네" 하고 넘어갔으면 잘못된 결론으로 최종 학습을 돌렸을 겁니다.

## 슬라이드 7 — 무엇이 성능을 올렸는지 분리해서 측정하기 (1.5분)

**그림**: `06_factor_decomposition.png`

**말할 내용**

증강과 하이퍼파라미터를 같이 바꾸면 **뭐가 효과가 있었는지 알 수 없습니다.**
그래서 2×2 설계를 만들었습니다.

| | 증강 OFF | 증강 ON |
| --- | --- | --- |
| optimizer auto | B00 (기준선) | B01 |
| Optuna 튜닝값 | B03 | B02 |

- `B03 − B00` = 순수 하이퍼파라미터 효과
- `B01 − B00` = 순수 증강 효과

이 구조를 세 개 노트북에 똑같이 넣고, **같은 조건끼리만** 비교했습니다.

결과가 흥미로웠습니다.

- **증강 효과**: 평균 **+0.0243**, 측정 18회 중 **17회 개선** (유일한 예외가 motion blur)
- **하이퍼파라미터 효과**: 평균 **−0.0115**, 측정 **6회 중 6회 모두 악화**

앞서 86클래스에서는 Optuna 튜닝이 38% 개선을 만들어냈는데, 17클래스에서는
**Ultralytics 의 `optimizer="auto"` 가 더 나았습니다.**

같은 기법이 조건에 따라 정반대 결과를 낸 겁니다. 데이터가 부족할 때는 튜닝이
크게 기여했지만, 충분해진 뒤에는 자동 설정이 더 잘 맞았습니다.

그래서 최종 설정은 **"증강은 mosaic, 옵티마이저는 auto"** 로 정했습니다.
이 조합 자체를 직접 돌려본 적은 없지만, 두 요인을 따로 측정했기 때문에
근거를 가지고 조합할 수 있었습니다.

## 슬라이드 8 — 클래스 불균형과 신문지 (1.5분)

**그림**: `07_class_balance.png`

**말할 내용**

17클래스로 묶은 뒤에도 클래스별 수량 차이는 남아 있었습니다.
특히 **신문지는 원본이 442장**밖에 없었습니다. 가장 많은 클래스(유리병 11,978장)의 **1/27** 수준이었죠.

두 가지로 대응했습니다.

**첫째, 오프라인에서 미리 4배로 증강**했습니다. 442장 → 1,736장.
이렇게 해서 최대/최소 클래스 격차를 **27배에서 6.9배로** 줄였습니다.

**둘째, 학습 중 증강에서는 신문지만 제외**했습니다. 이미 4배로 불려 둔 사진에
mosaic 까지 걸면 같은 원본이 계속 변형돼 나오는 **과증강**이 되기 때문입니다.

이 두 번째가 기술적으로 까다로웠습니다. Ultralytics 는 데이터 로딩을 여러
프로세스로 나눠 하는데, Windows 에서는 **dataset 객체를 pickle 로 전달**합니다.
그런데 pickle 은 객체 내용이 아니라 **클래스의 모듈 경로만** 저장합니다.
그래서 노트북 셀에서 정의한 클래스는 worker 프로세스가 import 하지 못합니다.

별도 파일(`selective_aug.py`)에 `YOLODataset` 서브클래스를 만들어 해결했고,
실제로 동작하는지 검증까지 했습니다.

```
전체 144,315장 중 증강 제외 1,736장 — 전부 신문지 확인
신문지: 2회 호출 결과 동일           → 증강 안 걸림
일반  : 3회 호출 중 2회 상이          → 증강 정상 작동
mosaic 상대 900회 추첨 중 신문지 0회  → 남의 mosaic 에도 안 들어감
```

## 슬라이드 9 — 최종 학습 (1.5분)

**그림**: `08_final_training_curve.png`

**말할 내용**

확정한 설정으로 최종 데이터셋 전체를 학습했습니다.

| | |
| --- | --- |
| 학습 데이터 | 144,315장 (clean 82.7% + 파손 17.3%) |
| epoch | 20 |
| 소요 시간 | **20.3시간** |
| 최종 mAP50-95 | **0.8638** |

학습 곡선에서 두 군데를 봐주세요.

**첫째, 초반 4~6 epoch 에서 잠깐 떨어집니다.** mosaic 으로 합성된 장면에
모델이 적응하는 과정입니다. 이후 회복해서 계속 올라갑니다.

**둘째, 마지막 4 epoch 에서 한 번 더 뜁니다.** `close_mosaic=4` 로 설정해서
17 epoch 부터 mosaic 을 껐는데, 그 구간에서 **0.8597 → 0.8637** 로
**+0.0040** 추가 상승했습니다.

앞서 버그로 만났던 그 `close_mosaic` 을 이번엔 제대로 써서 성능을 얻은 겁니다.

## 슬라이드 10 — "데이터가 제일 많으니 제일 좋은 모델인가?" (1분)

**그림**: `09_why_07_is_best.png`

**말할 내용**

정직하게 말씀드리면, **숫자만 보면 최종 모델이 1등이 아닙니다.**

중간 실험 중 하나가 **0.8670** 으로 최종 모델의 0.8638 보다 높습니다.

그런데 **이 둘은 비교 대상이 아닙니다.** 검증 세트가 완전히 다르기 때문입니다.

| | 검증 장수 | mAP50-95 |
| --- | --- | --- |
| 중간 실험 (04번) | 2,201장 | 0.8670 |
| **최종 모델 (07번)** | **10,548장** | **0.8638** |

최종 모델은 **4.8배 큰 검증 세트**에서 나온 수치입니다. 표본이 클수록 추정이
안정적이니, 같은 수치라도 최종 모델 쪽이 훨씬 믿을 만합니다.
게다가 최종 모델만 파손 이미지 17.3% 를 포함한 현실적인 조건에서 학습했습니다.

**"숫자가 높은 모델"과 "믿을 수 있는 모델"은 다릅니다.**

## 슬라이드 11 — 트러블슈팅 정리와 교훈 (1.5분)

**그림**: `troubleshooting.csv` 를 표로

**말할 내용**

이 외에도 여러 문제를 만났습니다. 특히 기억에 남는 걸 하나만 더 말씀드리면,

**배포된 모델이 학습한 모델이 아니었습니다.** 서비스가 읽는 `weights/best.pt` 를
확인해 보니 **COCO 80클래스 사전학습 모델**이었습니다. `person`, `bicycle`, `car`
같은 클래스를 출력하고 있었고, 그게 17개 재활용 클래스 이름에 잘못 매핑돼서
**모든 예측이 엉뚱하게 나가고 있었습니다.**

학습은 잘 되고 있었는데 그 결과가 서비스에 연결되지 않았던 겁니다.
지금은 학습 스크립트가 끝나면 자동으로 배포하도록 만들어 재발을 막았습니다.

**전체 트러블슈팅 8건**

| 구분 | 문제 | 해결 |
| --- | --- | --- |
| 설계 | 86클래스는 클래스당 89장뿐 | 17클래스로 재편 |
| 설정 | close_mosaic 로 mosaic 이 전 구간 꺼짐 | epoch 비율로 계산 |
| 배포 | best.pt 가 COCO 모델이었음 | 자동 배포로 변경 |
| 데이터 | 존재하지 않는 class 76 라벨 | manifest 대조 후 수정 |
| 실험 | Optuna 중단 후 재시작 불가 | 끊긴 trial 자동 정리 |
| 실험 | top-2 가 같은 trial 을 두 번 선택 | trial 기준 중복 제거 |
| 증강 | 신문지 과증강 | worker 까지 전달되는 서브클래스 |
| 환경 | PowerShell 이 UTF-8 로그를 깨뜨림 | 파이썬이 직접 기록 |

**핵심 교훈 세 가지**

1. **가장 큰 개선은 튜닝이 아니라 문제 재정의에서 나왔다.**
   86→17 클래스 재편 하나가 Optuna trial 41회보다 효과가 컸습니다.

2. **같은 기법도 조건에 따라 정반대 결과를 낸다.**
   하이퍼파라미터 튜닝은 데이터가 부족할 때 크게 기여했지만, 충분해진 뒤에는
   기본 설정이 더 나았습니다. "좋은 기법"이 아니라 "지금 조건에 맞는 기법"을
   찾아야 합니다.

3. **의심스러운 숫자를 그냥 넘기지 않는다.**
   소수점 6자리까지 같은 점수 4개가 설정 오류를 드러냈습니다.

# 예상 질문 대비

**Q. 왜 YOLO26n 같은 작은 모델을 썼나요? 더 큰 모델이 정확하지 않나요?**

서비스에서 실시간 응답이 필요했습니다. 현재 장당 1.33ms 인데, 더 큰 모델을 쓰면
정확도는 올라가겠지만 응답 시간과 서버 비용이 같이 올라갑니다.
0.86 이면 분리배출 안내에는 충분하다고 판단했습니다.
다만 더 큰 모델을 비교 실험하지는 않았으므로, 정확한 트레이드오프는
추가 검증이 필요합니다.

**Q. 17클래스로 묶으면서 정보가 손실되지 않나요?**

손실됩니다. 골프채와 일반 고철을 구분하지 못하게 됩니다. 다만 **배출 방법이
같으면 사용자에게는 같은 답**이므로, 서비스 관점에서는 손실이 아닙니다.
구분이 필요한 요구가 생기면 그때 해당 클래스만 분리하면 됩니다.

**Q. mosaic 이 왜 효과적이었나요?**

mosaic 은 이미지 4장을 한 장면으로 합칩니다. 그러면 (1) 한 화면에 여러 물건이
있는 상황을 학습하고, (2) 물건이 잘리거나 작게 보이는 경우를 보게 되고,
(3) 배경 다양성이 늘어납니다. 실제 사용자 사진과 비슷한 조건이라 효과가 있었다고 봅니다.

**Q. 최종 조합을 직접 실험하지 않고 정했다는 게 위험하지 않나요?**

맞습니다. 그래서 요인을 분리해서 측정했습니다. 증강 효과는 15/15 개선,
하이퍼파라미터 효과는 6/6 악화로 **양쪽 다 방향이 일관**됐습니다.
일관성이 없었다면 직접 측정한 조합을 썼을 겁니다.
결과적으로 최종 학습에서 0.8638 이 나와 예상 범위 안이었습니다.

**Q. 파손 데이터를 섞은 이유는?**

실제 사용자가 찍는 폐기물은 깨끗한 상태가 아닙니다. 찌그러진 캔, 젖은 종이 같은
것들이죠. 파손 이미지 17.3% 를 섞어 학습했고, 별도 실험(06-2)에서
성능 저하 없이 견고성을 얻을 수 있음을 확인했습니다.

**Q. 신문지 성능이 낮은데 괜찮나요?**

솔직히 말씀드리면 **이 부분은 저희 판단 착오였을 가능성이 큽니다.**

신문지 최종 mAP 는 **0.4396** 으로, 17개 클래스 중 유일하게 0.5 를 밑돕니다.
두 번째로 낮은 비철금속이 0.6855 이니 격차가 큽니다.

원인으로 의심하는 건 **저희가 신문지를 학습 중 증강에서 제외한 결정**입니다.
중간 실험(06-1)에서 신문지는 증강을 껐을 때 0.4136, mosaic 을 켰을 때 0.7680 으로
**증강 효과를 가장 크게 받는 클래스**였습니다. 그런데 최종 학습에서 얻은 0.4396 은
증강을 끈 쪽 수치에 가깝습니다.

"이미 오프라인에서 4배 증강했으니 추가 증강은 과증강"이라고 판단했는데,
결과적으로는 mosaic 을 같이 걸었어야 했던 것으로 보입니다.
신문지가 0.77 수준이었다면 전체 mAP 도 약 **+0.019** 올라 0.88 대가 됐을 것으로 추산합니다.

다음 학습에서는 `EXCLUDE_NEWSPAPER_FROM_AUG = False` 로 두고 다시 검증할 계획입니다.
설정 한 줄만 바꾸면 되도록 만들어 두었습니다.

**Q. 학습에 20시간이 걸렸는데 실무에서 감당 가능한가요?**

RTX 4070 Laptop 한 대 기준입니다. 학습은 한 번만 하면 되고, 추론은 1.33ms 이므로
서비스 운영에는 영향이 없습니다. 재학습이 잦아지면 더 큰 GPU 나 배치 크기 조정으로
줄일 수 있습니다.
