# 요구사항 정의서

**버전** v1.0 · **기준일** 2026-09-28

이 문서는 분리쏙 서비스의 요구사항을 상위 수준에서 정의합니다. 각 요구사항의 상세 입출력/처리
로직은 [04-requirements-specification.md](04-requirements-specification.md)에서 다룹니다.

**우선순위 기준**: 필수(서비스 핵심 흐름에 없으면 안 되는 기능) / 높음(주요 기능) / 보통(부가 기능)

---

## 1. 기능 요구사항 (Functional Requirements)

### 1.1 인증/회원

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-101 | 사용자는 이메일/비밀번호로 회원가입할 수 있다(지역은 가입 시 받지 않는다) | 필수 |
| FR-102 | 사용자는 이메일/비밀번호로 로그인해 JWT를 발급받을 수 있다 | 필수 |
| FR-103 | 사용자는 로그아웃할 수 있다(Stateless — 토큰은 클라이언트가 폐기) | 필수 |
| FR-104 | 사용자는 자신의 프로필(이메일, 선택 지역)을 조회할 수 있다 | 높음 |
| FR-105 | 비밀번호는 평문으로 저장되지 않는다(bcrypt 해시) | 필수 |

### 1.2 지역

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-201 | 로그인 여부와 무관하게 지원 지역 목록(56개)을 조회할 수 있다 | 필수 |
| FR-202 | 사용자는 자신의 거주 지역을 선택/변경할 수 있다 | 필수 |
| FR-203 | 지역 미선택 상태에서는 분석/배출정보/채팅 기능을 이용할 수 없다 | 필수 |

### 1.3 이미지 분석

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-301 | 사용자는 이미지를 업로드해 폐기물 분류를 요청할 수 있다 | 필수 |
| FR-302 | 시스템은 이미지에서 화면 중앙의 메인 객체를 탐지해 17개 분류 중 하나로 분류한다 | 필수 |
| FR-303 | 시스템은 Top-1 분류와 함께 대안 후보(Top-K)를 제시한다 | 필수 |
| FR-304 | 메인 객체를 찾지 못하면 재촬영을 안내한다(오류 아님, 저장하지 않음) | 필수 |
| FR-305 | Top-1 신뢰도가 임계값(기본 0.5) 미만이면 재촬영을 안내하되, 재학습 데이터로 활용하기 위해 저장은 수행한다 | 높음 |
| FR-306 | 업로드 이미지는 원본이 아니라 리사이즈·재인코딩된 형태로 저장·분석된다 | 높음 |
| FR-307 | 분석 성공 시 사용자의 선택 지역 기준 배출 요일/배출 방법을 함께 안내한다 | 필수 |
| FR-308 | 배출 정보 조회 실패는 분석 자체의 실패로 이어지지 않는다(경고만 표시) | 필수 |

### 1.4 피드백

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-401 | 사용자는 분석 결과가 맞다고 확인할 수 있다 | 필수 |
| FR-402 | 사용자는 제시된 다른 후보 중 하나를 최종 분류로 선택할 수 있다 | 필수 |
| FR-403 | 사용자는 제시된 후보에도 없으면 AI 재분석(재분류)을 요청할 수 있다 | 높음 |
| FR-404 | 재분석 결과도 17개 분류 범위 내에서만 나온다 | 필수 |
| FR-405 | 재분석이 유효한 결과를 내지 못하면 재촬영을 안내한다 | 보통 |
| FR-406 | 각 분석 건에 대한 피드백은 한 번만 제출할 수 있다 | 높음 |

### 1.5 AI Agent (후속 질문)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-501 | 사용자는 분석 결과에 대해 자연어로 추가 질문을 할 수 있다 | 높음 |
| FR-502 | 답변은 분석 컨텍스트(분류, 지역)와 배출 규정 지식(RAG)을 근거로 생성된다 | 높음 |
| FR-503 | 대화 내용은 저장되지 않는다(Stateless) | 필수 |
| FR-504 | AI 답변 생성이 불가능한 상황에서도 결정적(사전 정의된) 답변으로 대체해 서비스가 끊기지 않는다 | 보통 |

### 1.6 즐겨찾기

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-601 | 사용자는 특정 분류를 즐겨찾기에 등록할 수 있다 | 보통 |
| FR-602 | 사용자는 자신의 즐겨찾기 목록을 조회할 수 있다(최신순) | 보통 |
| FR-603 | 사용자는 즐겨찾기를 삭제할 수 있다 | 보통 |
| FR-604 | 같은 분류를 중복으로 즐겨찾기할 수 없다 | 낮음 |

## 2. 비기능 요구사항 (Non-Functional Requirements)

### 2.1 성능

| ID | 요구사항 |
|---|---|
| NFR-101 | Vision 추론은 이미지 1장당 평균 수십 ms 내외로 응답한다(모델 기준, 실측 baseline 약 7ms/image) |
| NFR-102 | 외부 연동(Vision/배출정보/RAG/Gemini)에는 개별 타임아웃이 설정되어 무한 대기를 방지한다 |
| NFR-103 | 분류 규칙 조회(RAG)는 반복 조회에 대해 캐시(`lru_cache`)로 응답 속도를 개선한다 |

### 2.2 가용성/장애 격리

| ID | 요구사항 |
|---|---|
| NFR-201 | 외부 서비스(Vision/RAG/Gemini/행정안전부 API) 중 하나가 장애 상태여도 Backend 헬스체크는 항상 정상이어야 한다 |
| NFR-202 | 부가 정보(배출요일, 배출방법 규정) 조회 실패는 핵심 기능(분석 성공)을 막지 않는다 |
| NFR-203 | DB 트랜잭션 실패 시 이미 업로드된 외부 저장소(S3) 객체는 보상 삭제되어야 한다(고아 객체 방지) |

### 2.3 보안

| ID | 요구사항 |
|---|---|
| NFR-301 | 모든 인증이 필요한 API는 JWT Bearer 토큰으로 보호된다 |
| NFR-302 | 비밀번호는 bcrypt로 해시하여 저장하고, 평문은 어디에도 남기지 않는다 |
| NFR-303 | 타 사용자의 리소스(피드백, 즐겨찾기)에는 접근할 수 없다(소유권 검증) |
| NFR-304 | Vision/RAG 내부 API는 Frontend에서 직접 접근할 수 없도록 네트워크 경계로 분리한다 |
| NFR-305 | S3에는 Presigned URL이 아닌 영구 Object Key만 저장한다(URL 만료로 인한 데이터 유실 방지) |

### 2.4 데이터 무결성

| ID | 요구사항 |
|---|---|
| NFR-401 | 분류 체계(`class_id`)는 YOLO 모델·DB·Frontend가 항상 동일한 단일 소스를 참조해야 한다 |
| NFR-402 | 피드백의 상태 조합(미응답/확인/정정)은 DB 제약(CHECK)으로 강제되어 잘못된 상태가 저장될 수 없다 |
| NFR-403 | 분석 시점의 Top-K 후보 스냅샷은 이후 사용자의 선택과 무관하게 변경되지 않는다 |

### 2.5 사용성

| ID | 요구사항 |
|---|---|
| NFR-501 | 재촬영이 필요한 상황은 오류 화면이 아니라 안내 화면으로 표시되어야 한다 |
| NFR-502 | 오류 메시지는 사용자에게 그대로 노출 가능한 한국어 문구로 제공되어야 한다 |
| NFR-503 | 분석 대기 시간 동안 사용자에게 진행 상태를 시각적으로 안내해야 한다 |
