# 타 팀 프로젝트 벤치마킹

**작성일** 2026-09-29

OJT 과정에서 함께 진행된 다른 팀들의 프로젝트 정의서를 검토하고, 분리쏙 발표 피드백에서
나온 지적(미지원 품목 처리, LLM 호출 절감, 북극성 지표, 가정값·실측값 구분 등)에 대한
구체적 해법을 다른 팀 사례에서 찾아 정리한 문서입니다.

## 검토한 문서

| 프로젝트 | 형태 |
|---|---|
| AdCheck (광고검수AI) | 건강기능식품 광고 과장·오인 가능성 분석 Chrome Extension |
| FILTERME (개인화 라이브 채팅) | AI 기반 YouTube 라이브 채팅 개인화 필터 Chrome Extension |
| Follow Up (회의 후속업무관리) | AI 기반 회의 후속 업무 관리 서비스 |
| Hub | 사내 자료 검색·업무 관리 AI 플랫폼 |
| 공농 (Gongnong) | AI 기반 한국수어 영상 변환 서비스 |

---

## 1. 프로젝트별 장단점

### AdCheck (광고검수AI Chrome Extension)

| 장점 | 단점 / 한계 |
|---|---|
| Rule Engine·RAG·AI를 역할별로 분리해 책임 경계가 명확함(AI는 후보 추출만, 최종 판정은 Rule Engine) | 마켓별 처리 편차가 큼(G마켓 53초, 429 오류 다수) — 아직 미해결 이슈로 남아있음 |
| `FindingRule[]`로 매칭된 규칙 전체를 보존하고, `reasonCode`로 "판단 시도 안 함"과 "애매함"을 구분 | 에러 메시지가 원인을 뭉뚱그림 — API 한도 소진도 "서버 연결 안 됨"으로 동일 안내 |
| 위반 여부에 따라 캐시 TTL을 7일/30일로 차등 적용해 AI 호출 비용 절감 | 재사용 캐시에 blind spot 존재(이미지 URL은 그대로 두고 내용만 바뀌면 미감지) |
| 실사용 테스트로 "판단 유보형" 설명 문구를 "행동 유도형"으로 교정하고 전/후 비교까지 검증 | 동일 입력에 대한 판정 안정성(재현성)이 여전히 "관찰 중" 상태 |
| "제품이 하지 않는 것"을 명시해 책임 범위를 스스로 한정 | |
| 트러블슈팅을 실측 수치로 기록(OCR 44초→12.6초 등), 비동기 API 패턴(제출/재사용판정 분리 + 폴링) | |

### FILTERME (개인화 라이브 채팅)

| 장점 | 단점 / 한계 |
|---|---|
| Local Pre-Processing으로 단순 도배·반복 메시지는 AI 호출 전에 걸러냄 | MVP 범위가 좁음(YouTube 단일 플랫폼, 카테고리 4종) |
| AI 분류 결과 + 사용자 Chat Profile을 분리했다가 Personalization Engine에서 결합 | 개인화가 재학습 없이 sensitivity 값 조정 수준에 머물러 깊이가 제한적 |
| AI 서버 장애 시에도 Local Filter로 전환해 서비스 자체는 무중단 | 정치/성적 표현 등 판단 기준 자체의 주관성 리스크에 대한 언급이 문서에 없음 |
| "거르고(필터)→넓히고(번역)→따라잡게 한다(AI매니저)"로 로드맵을 서사화해 확장 방향이 직관적 | |

### Follow Up (회의 후속업무관리)

| 장점 | 단점 / 한계 |
|---|---|
| AI 결과는 사용자 확정 전까지 실제 업무 데이터로 취급하지 않음(Human-in-the-loop 원칙이 데이터 정책에까지 반영) | Should/Could 단계 기능(대시보드, 우선순위 추천 등) 비중이 커서 P0 MVP 알맹이는 상대적으로 작음 |
| Success Metrics를 MVP 완료율/AI 검증/사용자 플로우 3단으로 구조화 | AI 분석 정확도에 대한 정량적 목표치가 문서에 구체적으로 없음 |
| 예외 정책이 "상황→처리" 1:1 표로 매우 깔끔하게 정리됨 | |
| AI Classification에 `PRIORITY_REASON` 필드를 둬서 추천 근거를 항상 노출 | |

### Hub PRD

| 장점 | 단점 / 한계 |
|---|---|
| "질문→답변→근거→원문 확인" 구조 + Content Hash·Version으로 근거 스냅샷을 고정(원본이 나중에 바뀌어도 과거 근거는 안 바뀜) | 검색+회의+TODO+Connector까지 스코프가 매우 넓어 MVP치고 과욕에 가까움 |
| 관리자가 질문 유형별로 AI 답변 근거 범위를 화이트리스트로 제한 가능 | Virtual Meeting·조직기억 등은 아직 구상 단계이고 검증 계획이 없음 |
| "AI는 후보를 만들고 사람은 판단한다" 원칙이 검색·회의·업무 전 기능에 일관되게 적용됨 | |
| Spring Boot(권한·상태)와 FastAPI(AI 실행)의 책임을 명확히 분리 — "AI가 권한과 업무 상태를 직접 결정하지 않는다" | |

### 공농 (Gongnong, 수어 번역)

| 장점 | 단점 / 한계 |
|---|---|
| 미지원 Gloss는 임의 대체하지 않고 자막 Fallback + 저신뢰 표시 — "정직한 실패" 원칙이 전 파이프라인에 일관 적용 | Gloss 커버리지(수어 단어 자산) 자체가 부족해 표현 가능 범위가 근본적으로 제한적 |
| Success Metrics에 "목표치·미실측"이라고 명시적으로 라벨링 | 성공지표 대부분이 아직 미실측 상태 — 실사용 검증 이전 단계 |
| 복지관 담당자 현장 인터뷰로 타깃 세그먼트(고령층) 근거를 실제 인용문으로 확보 | |
| 트러블슈팅을 발생증상/원인/해결방안/개선방안 4단 템플릿으로 일관되게 기록 | |

## 2. 우리 팀(분리쏙)에 적용하고 싶은 점

### 우선순위 높음 — 지금 코드에 바로 얹을 수 있는 것

1. **`reasonCode`/`match_type` 패턴 (AdCheck)** — [rag/src/agents/rule_lookup.py](../rag/src/agents/rule_lookup.py)가 정확 매칭 실패 시 major_category 내 유사도 폴백으로 조용히 넘어가는데, 이걸 "정확 매칭"과 "유사도 폴백"으로 구분해 응답에 실어야 발표 피드백이 요구한 "낮은 신뢰도는 자동 확정하지 않는다"를 실제로 구현할 수 있음.
2. **로컬 전처리/차등 캐싱으로 LLM 호출 절감 (FILTERME + AdCheck)** — [scripts/warm_rule_cache.py](../scripts/warm_rule_cache.py)는 규정 조회만 캐싱 중인데, 재분류(Gemini) 호출 앞단에도 confidence 임계값 기반 게이트나 "같은 이미지+지역" 재사용 캐시를 추가.

### 중간 우선순위 — 문서/프로세스 습관으로 정착

3. **목표치 vs 실측치 라벨링 (공농)** — 발표자료·문서에서 숫자 옆에 "실측"/"가정 시나리오"/"목표치(미검증)"를 태그로 명시하는 걸 팀 규칙으로.
4. **LLM 답변을 행동 유도형으로 마무리 (AdCheck)** — `rag/src/prompts/templates.py`의 답변이 "~일 수도 있어요"로 끝나는지 점검하고, "이렇게 배출하세요"형 결론으로 교정.
5. **에러 메시지가 원인을 숨기지 않게 점검 (AdCheck 반면교사)** — [docs/troubleshooting/README.md](troubleshooting/README.md)의 `RAG_SERVICE_UNAVAILABLE`/API 키 미설정 폴백이 사용자·운영자에게 원인 구분 없이 뭉뚱그려 보이지 않는지 확인.
6. **현장 인터뷰로 타깃 근거 보강 (공농)** — 1인 가구·신규 전입자 대상 짧은 인터뷰 2~3건으로 "왜 이 타깃인가"의 근거를 실제 인용문으로 확보.

### 낮은 우선순위 — 여유 있을 때

7. **북극성 지표를 3단 구조로 정리 (Follow Up)** — MVP 완료율 / AI 검증 정확도 / 사용자 플로우 완주율로 나눠서 발표.
8. **트러블슈팅에 실측 수치 습관화 (AdCheck, 공농)** — 모델 개선 전/후 수치를 기록하는 4단 템플릿(증상/원인/해결/개선)을 [docs/troubleshooting/README.md](troubleshooting/README.md)에도 적용.
9. **근거 스냅샷 고정 (Hub)** — 지자체 규정이 개정돼도 과거 답변의 근거가 안 바뀌도록 RAG 인덱스에 문서 버전 태그를 남기는 것 — 지금 당장보다는 장기 과제.
